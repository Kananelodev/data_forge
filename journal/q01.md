# q01 · Two Database


## In plain words

So we have ways of storing our data on a disk and we specifically have two ways:
While row store buries everything inside it, the column store puts the data next to each other so you don't read everything like in row store.
The `row store` is best used for finding data that we want and column store  is the one that we use when want to process a lot data.

## The proper terms

`Row store`: `OLTP` is for a lot of small, fast operations on whole records like inserting an order, looking up a customer
           : PostgreSQL, MySQL
`Columnar store`: This is for a few big queries that scan millions of rows but a few columns
                : Redshift, BigQuery, Snowflake, DuckDB         


## What I built

A cost model that measures how much data each layout has to read.
A decision rule that looks at a workload and picks a store.

## Where this shows up in real data engineering

So this shows up everywhere in the world of data engineering, every organisation well most of them have taken a liking of not choosing between the two kinds of storage but rather having both of them for different situations that might fit either database
We see these everywhere from our apps, banks and etc
